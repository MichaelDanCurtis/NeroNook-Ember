# Ember for Nero Nook

An independent native macOS plugin with reviewed task handoff, a durable Jobs card and this Mac’s signed Fuego Compute status. The plugin has its own account session, bundled Nook view and separate native window. Fuego owns execution, permissions and admission. No provider credentials or unrelated Nook context are copied.

The headless Fuego Compute LaunchAgent remains the owner of execution and gRPC authentication. Disabling this plugin or quitting Nero Nook closes only the monitoring client and its window. Already admitted compute jobs continue under the independent runtime.

The official local Nero Nook Creator generated this project. `Vendor/NookPluginSDK` is an exact independent SDK copy; `SDK-SNAPSHOT.json` records every copied file hash. The creator's recorded `hostBaseline` is its template baseline, 0.20.1. The source SDK copied here includes the current local host's 0.26.3 additions. This plugin negotiates only `dashboard-v1`, `panels-v1`, `custom-views-v1` and `actions-v1`; it has an ordinary-field/section fallback for older hosts.

## Build and verify

Requires macOS 14+, Swift 6/Xcode, and Python 3 for local authoring tools. The installed app has no Python dependency and does not link or compile the Nook host.

```sh
swift test
python3 Tools/nook.py test .
python3 Tools/nook.py pack . --identity 34B94A8687FA7F228A7AF7D8825A3CACD21239AC
```

`test` uses a separate ad hoc `.protocol-test` app identity and prevents a real compute connection. It checks old/current host handshake, SDK message validation, periodic snapshots and clean EOF. `pack` produces a new content-addressed, development-signed app and ZIP under `build/`. Install the app through Nero Nook Settings → Modules and review its declared read-only local connection. No host source or existing Nero Agent plugin changes are required.

Run the packaged, signed executable with `--check-compute` for one authenticated native status read without opening an app window. Success writes one redacted flat `BridgeStatus` JSON document to stdout. A failure writes a fixed safe explanation to stderr and exits nonzero. An unsigned/protocol-test build cannot satisfy the compute server's client identity requirement.

**Ask Michael before any new Apple notarization submission.** Local development signing and plugin installation do not imply notarization or public distribution.

## Native broker contract

The plugin connects only to `~/Library/Application Support/Fuego/Bridge/state/IPC/status.sock`. It checks every path ancestor through the current user’s home for a normal user-owned directory, requires a 0700 IPC directory and a 0600 user-owned socket, and verifies the kernel peer audit token against the exact Apple-signed `cloud.fuego.compute` identity and team `2GFVXB3249`. The server independently verifies `cloud.fuego.nook-agent` with that team. No bearer token or device private key is sent to this plugin.

Each connection carries one bounded newline JSON `version: 1`, UUID `requestId`, `operation: status` request (at most 2 KiB), and one response (at most 32 KiB). The response echoes that UUID and provides only these snapshot fields:

- `observedAt`, `validUntil`: local observation and expiry in Unix milliseconds, at most 15 seconds apart.
- `deviceId`, `provider`: device UUID and the qualified `codex` provider.
- `connection`, `sessionEpoch`, `ready`, `lastGatewayAt`: native bridge phase, current epoch, explicit readiness, and the last received authenticated current-session gateway frame. A fresh local poll does not refresh gateway liveness.
- `paused`, `activeJobs`, `uncertainJobs`: current local admission/execution summaries.
- `recentJobs`: at most 20 unique run/command UUID pairs and an allowlisted lifecycle state.

The client rejects unknown metadata fields, mismatched requests, malformed IDs/counts/states, excessive jobs/bytes, stale/future observations, or inconsistent readiness. Connected status requires a received gateway frame within 30 seconds. Ready additionally requires the server’s explicit readiness flag and no pause. Local pause blocks new work and requests active jobs to stop; the UI does not claim that cancellation has completed.

All connect/send/receive waits share one monotonic three-second I/O budget. Slow partial reads do not renew it. Cancelled or superseded reads cannot revive the UI. The plugin polls every two seconds while its process is alive, clears failed/expired state immediately, and never persists status or recent job metadata.

The bundled HTML/CSS/JavaScript receives bounded scalar view state through the SDK. It uses text content for runtime data and has no direct networking, arbitrary file bridge, media permissions or remote frames. The native client owns all IPC.

## Generic Nook integration

`read_status` is a read-only action with no arguments, and `status` is a four-second state channel. Both use the same eight bounded scalar fields: `available`, `connected`, `ready`, `phase`, `active_jobs`, `uncertain_jobs`, `paused`, `observed_at`. Other Nook plugins need explicit host grants to access them. Recent-job IDs remain in Fuego’s own view rather than the cross-plugin export. A routing grant does not authorize sending this data to an AI provider or Fuego server.

Selected desktop/messaging events and remote control remain later slices. Reviewed per-user task handoff is now implemented separately from this monitor. This monitor does not claim the full M4 desktop/Ember milestone.


## Naming and Nero Flow

Ember is this independent assistant module. Fuego is its backend and account service; Nero Flow is NeroNook’s local workflow editor. This module retains `cloud.fuego.nook-agent` and existing handoff capability definitions so saved grants, workflows and Stream Deck bindings are not silently invalidated. Legacy action titles still mention Fuego. Preparing a task never sends it; review the target and task before Send.
